#### ✅ 优惠券充值接口描述增强

**接口**: `POST /api/user/recharge-with-coupon`

**更新内容**:
```
⚠️ 重要说明：
- 充值只增加人民币余额，不直接增加点数
- 优惠券用于减少实际支付金额
- 需要使用余额购买套餐才能获得点数

请求体：
- amount: 充值金额（元）
- couponId: 优惠券ID（可选）

返回数据：
- success: 是否成功
- amount: 原始金额
- actualAmount: 实际支付金额（扣除优惠后）
- discount: 优惠金额
- balanceBefore: 充值前余额
- balanceAfter: 充值后余额
```

#### ✅ 创建套餐模板接口描述全面升级

**接口**: `POST /api/admin/packages/create`

**更新内容**:
```
⚠️ 重要说明：
- 套餐代码（packageCode）必须唯一
- 越贵的套餐应该设置更高的性价比（每元获得的点数更多）
- 套餐一旦创建，用户即可购买

关键字段：
- packageCode: 套餐代码（必填，唯一标识）
- packageName: 套餐名称（必填）
- identityLabel: 身份标识（可选）
- points: 包含点数（必填）
- price: 价格（必填）
- durationDays: 有效期天数（可选）
- dailyCallLimit: 每日调用限制（可选）
- monthlyCallLimit: 每月调用限制（可选）
- maxTokensPerCall: 单次最大Token数（可选）
- priorityLevel: 优先级等级（可选）
- features: 特性说明（可选）
- sortOrder: 排序顺序（可选）

示例（体现越贵越划算）：
- 基础版: 29.9元 = 100点 (每元3.34点)
- 专业版: 99.9元 = 500点 (每元5.01点) ✅
- 旗舰版: 299.9元 = 2000点 (每元6.67点) ✅✅
```

**关键改进**:
- ✅ 强调"越贵越划算"的配置原则
- ✅ 列出所有关键字段及其说明
- ✅ 提供具体的配置示例
- ✅ 用数字直观展示性价比梯度

#### ✅ 更新套餐模板接口描述增强

**接口**: `PUT /api/admin/packages/update`

**更新内容**:
```
⚠️ 注意事项：
- 只能更新部分字段，不能修改 packageCode

可更新字段：
- id: 套餐ID（必填）
- packageName: 套餐名称
- description: 套餐描述
- identityLabel: 身份标识
- points: 包含点数
- price: 价格
- ...（其他字段）

建议：
- 调整价格时保持"越贵越划算"的原则
- 下架套餐前确认没有活跃订阅
```

#### ✅ 上架/下架套餐接口描述增强

**接口**: `POST /api/admin/packages/toggle-status`

**更新内容**:
```
⚠️ 重要说明：
- 下架的套餐用户无法购买，但已购买的订阅仍然有效
- 上架的套餐会立即对用户可见
- 常用于：临时促销、库存不足、套餐调整等场景

请求体：
- id: 套餐ID（必填）
- status: 状态（必填），1-上架，0-下架

使用场景：
- 节假日促销活动：先下架旧套餐，上架限时优惠套餐
- 库存管理：某套餐点数不足时暂时下架
- 套餐优化：调整套餐内容后重新上架
```

**关键改进**:
- ✅ 说明下架不影响已有订阅
- ✅ 列出3个典型使用场景
- ✅ 提供实际操作建议

---

#### ✅ 删除套餐模板接口描述增强

**接口**: `DELETE /api/admin/packages/{id}`

**更新内容**:
```
⚠️ 警告：
- 删除操作不可恢复！
- 只能删除没有被任何用户购买的套餐
- 如果有活跃订阅，需要先处理完所有订阅

建议流程：
1. 先下架套餐（status=0）
2. 等待所有订阅过期
3. 确认没有活跃订阅后再删除

或者：
- 如果只是不想让用户购买，建议使用"下架"而不是"删除"
- 下架可以保留历史数据，方便后续统计和分析
```

**关键改进**:
- ✅ 强调删除操作的危险性
- ✅ 提供安全的删除流程
- ✅ 建议使用"下架"替代"删除"
- ✅ 说明数据保留的重要性
